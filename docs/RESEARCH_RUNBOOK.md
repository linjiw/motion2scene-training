# Continuing research from the package

1. Start from [setup](SETUP.md), check the required workflow profile, verify/unpack data, and read [the design map](WORKFLOWS.md). Record the Git commit and input hashes for every new experiment.
2. Run `student-smoke --updates 24`, `generator-smoke --updates 20`, and `scene-tasks` into fresh output directories. Receipts confirm execution; these checks do not establish physical improvement.
3. Prepare a bounded teacher configuration with `teacher-prepare --iterations 10 --num-envs 128`. Review `command.json`, `composed-config.yaml`, `plan.json` and `loader-validation.json`. Once native readiness is established, `teacher-train PACKET` executes it. Use a separate newly prepared 32,000-iteration packet for the intended large experiment; do not silently expand the smoke budget.
4. Retain the final training receipt and checkpoint. Reevaluate the previous teacher and candidate under the same repaired development data, seed and environment configuration. Native evaluation implementation lives in `vendor/sonic/gear_sonic/eval_agent_trl.py` and the tracking qualification callback. **There is currently no portable one-command teacher-evaluation wrapper**: archived evaluation commands require newly bound checkpoint/output/motion paths and a matching config beside the checkpoint. Evaluation is not automatically queued by `teacher-train`. The packaged [teacher transition report](sonic/motion2scene/BFM_REPAIRED_TEACHER_TRANSITION_20260912.md) records the checkpoint-1400 comparison used by the current distillation studies.
5. For new BFM data, use the source collection/aggregation interfaces with hashes from the chosen teacher. Preserve original reference phase, query-support masks, split membership and actual intervention counts. Never mix old-teacher labels with a new decoder without explicit matching validation.
6. The full foundation fitter is `gear_sonic.research.scene_distillation.train` (`--config JSON --output DIR`), launched from `vendor/sonic` with its directory on `PYTHONPATH`. Fresh initialization, weights-only initialization and exact optimizer continuation are distinct. Exact BFM continuation uses `resume_checkpoint`/`resume_sha256`, preserves optimizer/RNG state and rejects changed learning rate, curriculum, sampling or dataset identity. Use a new output directory. For the stronger preserved-motor path, read [the motor recovery result](sonic/motion2scene/BFM_MOTOR_RECOVERY_RESULTS_20260913.md) before using `motor_training.py` or `online_motor.py`.
7. Teacher `teacher-train` does **not** implement a portable crash-resume command. It refuses reused attempts. Preserve the checkpoint and measured budget after interruption; a teacher continuation design must reconcile optimizer, motion sampling, simulator state and remaining budget. Re-running `teacher-prepare` starts a new release-initialized fit, not a continuation.
8. Scene tasks are unqualified proposals. Require contact, goal-hold and motion-quality qualification before scene-navigation distillation. The current navigation command adapter uses `navigation_motor.py`; its positive data loader accepts only task-success-bound demonstrations. Recovery data additionally requires the receipt and suffix checks in `navigation_recovery_data.py`. Keep bounded residual PPO gated on a qualified foundation and task setup. Do not relabel sparse-command reference-tracking failures, failed takeovers or privileged interventions as autonomous goal-navigation results.

Use the same held-out split and declared metrics rather than tuning on repeated development looks. Keep physics steps, optimizer updates, attempted motion counts and actual outcomes in the research ledger. The archived research has negative results and retractions; retain them when constructing new comparisons.

The CPU/data workflows are reusable now. Native bootstrap, generic teacher continuation, one-command evaluation and the registered supported-recovery physical result are explicitly unfinished integration areas, not hidden prerequisites already claimed complete. The [distillation research report](DISTILLATION_RESEARCH.md) gives the proposed stable interfaces, data tiers, offline/online loop and staged navigation-context evaluation plan.
