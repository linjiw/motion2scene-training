# Status and research roadmap — September 23, 2026

This document takes stock of the project. It maps the target architecture (motion prior → SONIC-style tracker → perceptive teacher–student distillation → masked control interface → G1 with MID-360/D435i) onto what the repository has actually measured. It then names the bottlenecks and proposes an ordered plan. It supersedes the status lines in the README and the September 13 update. The per-experiment reports stay authoritative for their own numbers.

## 2. How the notes line up with the evidence

The notes' main architectural advice matches what this repository already found the hard way:

- **Don't put the generative model at joint level.** The action-flow and direct-regression heads both fail, while the pretrained SONIC decoder works. Flow matching belongs in a planner that emits a *future motion chunk*, and a fast tracker executes it.
- **Separate motor transfer, task abstraction and observation transfer.** The motor student succeeds, while the known-map goal student is the current bottleneck. Adding sensors now would only obscure where failures come from.
- **Offline → online (DAgger) hybrid.** The offline fit gives most of the motor gain. Short-cycle DAgger is what moved navigation.
- **Mask with explicit validity, not zeros.** Already done (availability masks). The typed-token variant is a reasonable later refactor.

Where the notes need correcting or checking before anything is cited:

- SONIC compute: one note says 9k GPU-hours (preprint), the other 21k (final). Cite the version you actually read.
- Several 2026 arXiv IDs (Perceptive BFM 2606.08059, Athena-WBC 2607.04837, 2604.17335, SCRIPT 2605.22894, etc.) have not been checked against the papers. Check each before it enters related work.
- "Fast LiDAR" is FAST-LIO2, an odometry/mapping algorithm; the sensor is the MID-360. The policy's voxel grid is a separate design choice and should not be tied to Faster-LIO's iVox structure.
- SONIC is trained directly with PPO; it is not a teacher–student setup. Our "teacher" is a SONIC checkpoint fine-tuned on our clips, and it is a *reference tracker*, not a navigation expert. That distinction drives bottleneck A below.

## 3. The three bottlenecks

### A. There is no goal-conditioned expert to distill from

Every navigation label comes from a tracker following a fixed reference on a nominal clock. DAgger requires an expert that can label *any* visited state. A reference tracker can only do that near its reference, so yield drops from 18/19 at 15% takeover to 3/19 at 75% ([stopping study](sonic/motion2scene/NAV_8192_STOPPING_20260913.md)). The recovery machinery built since then (switch fractions, supported suffixes, approach weighting, phase rewind) all compensates for this missing expert. The phase-rewind probe (6/32 timely vs 0 nominal) shows what is missing: **re-timing and re-routing the reference**, which is a planning function.

**Proposed fix:** a privileged, goal-conditioned *traversal teacher*, trained with PPO. It acts in SONIC token/command space over the frozen decoder: a residual on the motor student's 114-D command, or a latent action. It sees exact scene geometry (SDF / occupancy around the body), goal and terminal requirements. Rewards: goal progress, the 50-tick stop/hold, contact penalties, and a style/tracking prior toward the motion manifold. This is the Parkour-in-the-Wild / HOVER pattern: the oracle comes from RL, and the student is distilled by DAgger. It turns DAgger from "salvage the states the tracker can still reach" into "label every state". The current adapter becomes a warm start and a baseline.

### B. Evaluation cannot separate the arms

The panel has 19 tasks, runs sequentially (about 1 h per arm-panel, up to 25 min per long task under contention) and is scored on one seed. The evaluation seed alone moved a checkpoint from 4/24 to 1/24. Until evaluation is cheap enough to run 3–5 seeds routinely, results like 2 vs 7 cannot be ranked.

**Proposed fix:** vectorized evaluation, with all tasks × seeds as parallel envs in one Isaac process (the teacher already trains at 8192 envs). Report success as mean ± interval over seeds. Also widen the panel beyond one ancestry group before claiming generalization.

### C. The motor foundation is narrow

Fine-tuning SONIC on ~100 clips raises train completion and lowers dev completion (8/20 → 6/20). The 8192-env teacher shows the same pattern. The student inherits that ceiling (~10/20 dev). The notes' "strong motion foundation first" is right, and we currently get it by *not* over-fitting the released model.

**Proposed fix:** make the released SONIC checkpoint the default foundation. Fine-tune only with a held-out gain gate, and grow the motion set, including scene-conformal variants generated through the Kimodo constraint interface: narrow-gap, crouch-under, side-step, stop/turn. Motion diversity matters more here than more PPO iterations on 89 clips.

## 4. Target architecture, adapted to this repository

```
goal / velocity / waypoint / keypoints  (+ validity masks)
            │
 privileged scene (SDF, occupancy) ─► [Traversal teacher, PPO in SONIC command/token space]  ◄─ training only
            │                                   │ DAgger labels (command + future chunk + risk)
 onboard obs (proprio, height map / voxel) ─► [Perceptive student]
            │                                   │
            └─► optional planner: flow-matching future reference chunk (≈10 frames, 50 Hz)
                                                ▼
                         frozen SONIC encoder → FSQ token → decoder → 29 joint targets
```

- The student's output interface stays the SONIC token/command, which is known to work. A flow planner, if added, emits the *10-frame future reference* the teacher already consumes. That is the interface on which the teacher scores 19/24.
- Distillation losses: command/action, future-chunk, and a small risk/clearance head (the notes' "distill affordance, not reconstruction"). Add representation alignment only if action-only DAgger plateaus.

## 5. Ordered plan with gates

| # | Work | Gate to proceed |
|---|---|---|
| 0 | Confirm approach-DAgger c2 (7/19) and uniform c2 on seeds 91262/91264 | Mean ≥ 5/19 across 3 seeds, or drop approach weighting as a claim |
| 1 | Vectorized multi-seed evaluation harness for the stopping panel | Reproduces sequential per-task results on a fixed seed; ≥ 5× faster |
| 2 | Foundation check: released SONIC vs fine-tuned teachers as the motor anchor, on dev and the stopping panel | Choose the foundation by held-out numbers |
| 3 | Privileged goal-conditioned traversal teacher (PPO, command residual over the frozen motor, exact local SDF/occupancy) on the 24-task family, then a larger procedurally generated clear/corridor/obstacle family | Teacher ≥ 90% on the feasible panel across seeds, with goal changes producing different behavior |
| 4 | DAgger the known-map student from that teacher (reuse `navigation_motor` fit, recovery receipts, masks) | Student within 10 points of teacher; stop labeling via reference recoveries |
| 5 | Replace primitives with a raycast height map (Isaac Lab `RayCasterCfg` + `GridPatternCfg`) and then a head-mounted MID-360-proxy voxel grid (`LidarPatternCfg`, −7°…52° FOV); teacher unchanged, student observation swapped | Height-map student ≈ known-map student on ground-level tasks; voxel needed only once overhang/low-clearance tasks exist |
| 6 | Masked interface: goal-only / velocity / waypoint / keypoint modes trained jointly, uniform masking as baseline | Goal-only ≥ 80% of full-reference success |
| 7 | Flow-matching planner (future reference chunk) vs direct command student | Beats direct student on multimodal scenes (left/right bypass) at equal teacher budget |
| 8 | Sensor realism (latency, dropout, per-ray time offsets, self-occlusion), then MuJoCo sim-to-sim, then G1 | Per the notes' sim-to-real checklist |

Leave audio and RGB semantics out until a task needs them.
